# another-dove-jam

多人协作的 Godot 游戏方案实验仓库。

## 仓库定位

- `main` 只保存共同约束、协作规范、模板和跨分支决策，不直接承载某位开发者的独立游戏实现。
- 每位开发者在自己的独立分支中完成一套独立游戏方案的讨论、设计、原型和实现。
- 各独立方案默认互不依赖、互不覆盖，不要求共享玩法、剧情、美术或目录结构。
- 在团队正式选定某一方案之前，不把某个开发者的游戏实现直接合入 `main`。

## 推荐分支命名

```text
proposal/<developer>/<game-slug>
```

例如：

```text
proposal/alice/arena-game
proposal/bob/puzzle-game
```

每名开发者可以维护一个或多个 proposal 分支，但每个分支应只对应一个清晰的游戏方案。

## Main 分支职责

`main` 负责维护：

- 协作规则与分支边界
- Godot 项目的共同技术约束
- 游戏方案文档模板
- PR 检查规则
- 团队已经达成一致的跨分支决策

`main` 不负责维护：

- 某个独立方案的玩法设计
- 某个独立方案的 Godot 场景、脚本、资源或关卡
- 尚未经过团队确认的公共架构

详细规则见 [`docs/COLLABORATION_RULES.md`](docs/COLLABORATION_RULES.md)。

## 基本流程

1. 从最新 `main` 创建自己的 `proposal/<developer>/<game-slug>` 分支。
2. 在分支内先补齐游戏方案文档，再进行原型或实现。
3. 独立方案的普通开发不需要向 `main` 提交 PR。
4. 只有共同约束、公共模板、跨分支约定需要向 `main` 提交 PR。
5. 如果团队决定采用某个方案，再通过单独决策 PR 明确后续整合方式，不默认把整个 proposal 分支直接倾倒进 `main`。

这套结构的目的很简单：允许每个人把创意做完整，同时避免所有人同时修改同一套游戏代码。
