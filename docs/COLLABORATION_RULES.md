# Collaboration Rules

## 1. 核心原则

本仓库采用“共享规则 + 独立方案分支”的协作方式。

- `main` 是规则基线，不是多人共同开发某一款游戏的代码主干。
- 每个游戏方案必须在独立 proposal 分支中自行闭环。
- 不允许为了“复用方便”直接修改其他开发者的 proposal 分支。
- 不要求不同 proposal 分支保持玩法、代码架构、目录结构或美术方向一致。
- 任何跨分支约束都必须先进入 `main`，再由各 proposal 分支自行同步。

## 2. 分支模型

### 2.1 Main

`main` 只接受以下内容：

1. 协作规则、贡献说明和模板。
2. Godot 共同约束。
3. 通用 Git/GitHub 配置。
4. 团队明确同意的跨分支决策。
5. 不绑定某个具体玩法的公共工具规范。

在“方案探索阶段”，`main` 不接受：

- 某个具体游戏的 `project.godot`
- 具体游戏场景、脚本、关卡、角色、Boss、技能实现
- 某个方案专属的剧情、美术、数值或设计文档
- 为某个方案强行规定其他分支必须采用的代码架构

### 2.2 Proposal 分支

命名：

```text
proposal/<developer>/<game-slug>
```

要求：

- 一个分支只表达一个游戏方案。
- 从当时最新的 `main` 创建。
- 分支内可自由包含 Godot 项目、设计文档、原型、资源和测试。
- 方案分支拥有自己的技术选择权，只要不违反 main 的硬性约束。
- 开发者不得把自己的 proposal 分支作为其他 proposal 的“公共基座”。

如果同一开发者要推翻核心玩法，优先创建新的 proposal 分支，而不是把旧方案改得无法追溯。

## 3. 每个 Proposal 的最低交付内容

每个方案至少应包含：

```text
README.md
project.godot            # 开始制作原型后需要
docs/
  GAME_DESIGN.md
  DECISIONS.md
  PLAYTEST.md             # 有可玩原型后需要
```

`README.md` 至少说明：

- 游戏名称/代号
- 一句话玩法
- 目标玩家数量
- 目标平台
- 使用的 Godot 精确版本
- 当前阶段：idea / design / prototype / playable
- 如何启动

`GAME_DESIGN.md` 至少说明：

- 核心循环
- 玩家目标
- 主要操作
- 胜负条件
- 一局时长预期
- MVP 内容
- 明确不做的内容

## 4. Godot 共同约束

所有 proposal 必须使用 Godot，引擎精确版本由各 proposal 在 README 中声明。在团队决定整合某个方案以前，`main` 不强制所有方案使用完全相同的小版本。

共同要求：

- 不提交 `.godot/` 导入缓存。
- 不提交编辑器本地状态或临时文件。
- 不依赖只存在于某位开发者电脑上的绝对路径。
- 第三方插件、字体、音频、模型和贴图必须记录来源与许可。
- 大型二进制资产应控制数量；明显不适合直接放 Git 的内容应使用 Git LFS 或外部资产来源说明。
- 项目必须能从干净 clone 后按 README 启动。

## 5. 方案之间的边界

允许：

- 阅读其他 proposal 的设计和代码。
- 在自己的 proposal 中重新实现相似想法。
- 通过 Issue/讨论提出跨方案建议。
- 经原作者同意后抽取真正通用的做法。

禁止：

- 直接向其他开发者的 proposal 分支推送未经确认的改动。
- 用 main 强迫其他 proposal 接受某个方案专属设计。
- 在没有团队决策的情况下，把某个 proposal 宣布为正式主线。
- 为减少冲突而让所有开发者共用同一个 Godot 项目目录。

## 6. Main 的变更流程

对 `main` 的修改应通过 PR 完成。PR 应说明：

1. 修改了哪条共同约束。
2. 为什么这是跨 proposal 的共同问题。
3. 是否会要求现有 proposal 做迁移。
4. 是否存在破坏性影响。

规则变更不得偷偷夹带某个具体游戏实现。毕竟“顺手塞进去”通常是协作项目最朴素的灾难生成器。

## 7. 同步 Main

proposal 分支可以按需要同步 `main` 的新规则。

推荐方式：

```bash
git fetch origin
git checkout proposal/<developer>/<game-slug>
git merge origin/main
```

规则变更如果与方案实现冲突，由 proposal 作者自行决定如何适配；不得通过反向修改 main 来迁就单个方案，除非原规则确实需要团队重新讨论。

## 8. 方案评审与选型

探索阶段不以“谁最先写代码”为胜出条件。

建议评审至少考虑：

- 核心玩法是否清晰
- 5 分钟内是否能理解并开始游玩
- 是否存在可重复的乐趣循环
- MVP 是否能在团队时间内完成
- 技术风险和资产成本
- 多人合作时的开发拆分难度
- 当前原型的可玩性与试玩反馈

当团队决定采用某个方案时，应先在 `main` 增加一条正式决策记录，再决定：

- 是否改变 main 的职责
- 是否从选中 proposal 创建新的正式开发分支
- 是否保留其他 proposal 作为实验分支

不要直接把整个 proposal 强行 merge 到 main，然后让 Git 替团队完成产品决策。Git 没有这个能力，人类有时也没有，但至少应该尝试。

## 9. 决策记录

影响多个 proposal 的决定必须记录在 `docs/DECISIONS.md`。

每条至少包含：

- 日期
- 决策
- 原因
- 影响范围
- 是否需要 proposal 迁移

仅影响单一游戏方案的决定，记录在该 proposal 自己的 `docs/DECISIONS.md`，不要污染 main。
